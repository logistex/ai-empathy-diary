## 1. 개요 (Overview)

**AI 공감 다이어리**는 사용자가 한 줄 일기를 쓰면, AI가 그 글에 담긴 감정을 분석하고 따뜻한 공감·위로 메시지를 돌려주는 웹 일기 앱이다. 하루의 감정을 짧게 기록하고 싶지만 혼자 쓰는 일기가 공허하게 느껴지는 사용자를 위해, "쓰면 반응이 돌아오는" 정서적 상호작용을 제공한다. 구글 로그인으로 사용하며, 일기 데이터는 사용자별로 완전히 분리되어 안전하게 저장된다.

- **무엇을**: 감정 분석 + 공감 메시지가 결합된 한 줄 일기 앱
- **누구를 위해**: 감정 기록·정서적 위로를 원하는 개인 사용자
- **왜**: 기록의 부담은 줄이고("한 줄"), 기록의 보상은 늘린다("AI의 공감")

---

## 2. 문제 정의 (Problem)

- **일기의 진입 장벽**: 일기를 쓰려면 "무엇을, 얼마나" 써야 할지 부담스럽다. 대부분의 사람은 며칠 만에 포기한다.
- **일방향 기록의 공허함**: 기존 일기 앱은 글을 저장할 뿐, 아무 반응이 없다. 감정을 털어놓아도 되돌아오는 것이 없다.
- **정서적 지지에 대한 니즈**: 힘든 하루 끝에 "괜찮다"는 말 한마디가 필요하지만, 매번 사람에게 말하기는 어렵다.

**근거/전제**: 위 문제 인식은 제품 콘셉트의 기반 가정이며, 정량적 사용자 리서치로 검증된 값은 아니다(3장 페르소나·9장 성공 지표 참조). → ❓확인 필요: 초기 사용자 인터뷰/설문 데이터 유무.

## 3. 목표 (Goals & Non-goals)

### 3.1 목표 (Goals)

- **G1. 낮은 마찰의 감정 기록**: 로그인 후 3클릭 이내, 한 줄 입력만으로 일기 작성이 완료된다.
- **G2. 의미 있는 AI 반응**: 작성한 일기에 대해 감정 라벨과 공감 메시지를 즉시(체감 지연 최소화) 돌려준다.
- **G3. 안전한 개인 공간**: 구글 로그인 기반으로 사용자별 데이터가 분리되며, 타인의 일기는 절대 노출되지 않는다.
- **G4. 되돌아보기**: 과거 일기와 감정 흐름을 히스토리에서 확인할 수 있다.
- **G5. 완주 가능한 MVP**: 5단계 에이전트 파이프라인으로 배포까지 완성한다(`PLAN.md`).

### 3.2 비목표 (Non-goals) — 이번 범위 밖

- 감정 통계·차트/추세 시각화(그래프, 감정 캘린더 등) — 향후 고려.
- 소셜 기능(공유, 팔로우, 댓글, 공개 피드).
- 다중 로그인 수단(카카오/애플/이메일-비밀번호) — 이번엔 구글만.
- 알림/리마인더(푸시·이메일), 정기 회고.
- 일기 수정 기능(작성 후 편집) — MVP는 작성/조회/삭제까지만(삭제 포함 여부는 5장·6장 참조).
- 네이티브 모바일 앱(반응형 웹으로 대응).
- AI 상담·치료적 개입(의료·심리 상담 대체 아님).

## 4. 타깃 사용자 / 페르소나 (Users)

### 4.1 핵심 사용자

감정을 짧게 기록하고, 그에 대한 정서적 반응을 받고 싶은 개인. 스마트폰·데스크톱 웹에 익숙하고 구글 계정을 보유.

### 4.2 페르소나

**페르소나 A — "하루를 정리하고 싶은 지우" (26세, 직장인)**
- 니즈: 잠들기 전 오늘 하루 감정을 한 줄로 남기고 싶다.
- 페인 포인트: 일기 앱을 여러 번 시도했지만 "쓸 게 없어서" 금방 그만뒀다.
- 기대: 짧게 써도 뭔가 반응이 오면 계속 쓰게 될 것 같다.

**페르소나 B — "위로가 필요한 현우" (21세, 대학생)**
- 니즈: 힘든 날 누군가에게 말하고 싶지만 부담 없이 털어놓을 곳이 필요하다.
- 페인 포인트: 친구에게 매번 감정을 쏟아내기 미안하다.
- 기대: 판단 없이 공감해 주는 반응.

→ ❓확인 필요: 실제 타깃 연령/직군의 우선순위(위 페르소나는 콘셉트 기반 가정).

## 5. 사용자 스토리 (User Stories)

- **US-1 (로그인)**: 사용자로서, 내 일기를 안전하게 보관하기 위해, 구글 계정으로 로그인하고 싶다.
- **US-2 (작성)**: 로그인한 사용자로서, 오늘의 감정을 남기기 위해, 한 줄 일기를 작성하고 저장하고 싶다.
- **US-3 (공감 수신)**: 일기를 쓴 사용자로서, 위로받기 위해, 내 글에 대한 감정 분석과 공감 메시지를 즉시 받고 싶다.
- **US-4 (히스토리)**: 사용자로서, 지난 감정을 되돌아보기 위해, 과거에 쓴 일기 목록을 시간순으로 보고 싶다.
- **US-5 (데이터 분리)**: 사용자로서, 사생활을 보호받기 위해, 오직 내 일기만 보이고 남의 일기는 절대 보이지 않길 원한다.
- **US-6 (로그아웃)**: 사용자로서, 공용 기기에서 안전하게 벗어나기 위해, 로그아웃하고 싶다.
- **US-7 (에러 회복)**: 사용자로서, AI 응답이 실패하더라도 내 일기는 잃지 않고, 무엇이 잘못됐는지 알고 다시 시도하고 싶다. → ❓확인 필요: AI 실패 시 일기 저장 정책(6장 FR-3 참조).

## 6. 기능 요구사항 (Features)

우선순위: **P0**(MVP 필수) / **P1**(있으면 좋음) / **P2**(향후).

### FR-1. 구글 로그인 / 인증 · **P0**
- Auth.js를 통한 구글 OAuth 로그인·로그아웃.
- 최초 로그인 시 `users` 테이블에 `google_sub`(고유), `email`, `name`, `image` 저장/갱신.
- 미인증 사용자는 작성·히스토리 화면 접근 불가(로그인 화면으로 리디렉션).
- **수용 기준(AC)**:
  - [ ] 구글 계정으로 로그인하면 작성 화면으로 이동한다.
  - [ ] 미로그인 상태로 `/write`·`/history` 접근 시 로그인 화면으로 리디렉션된다.
  - [ ] 동일 구글 계정으로 재로그인 시 기존 `users` 레코드를 재사용한다(중복 생성 없음).
  - [ ] 로그아웃하면 세션이 종료되고 로그인 화면으로 돌아간다.

### FR-2. 한 줄 일기 작성 · **P0**
- 텍스트 입력창 + 저장(작성) 버튼.
- 저장 시 `POST /api/diary`에 `{ content }` 전송(로그인 필요).
- **수용 기준(AC)**:
  - [ ] 내용을 입력하고 저장하면 서버에 전송되고 로딩 상태가 표시된다.
  - [ ] 빈 내용은 저장할 수 없다(버튼 비활성 또는 검증 메시지).
  - [ ] 저장된 일기는 현재 로그인 사용자(`user_id`)에 귀속된다.
  - [ ] 입력 최대 길이 제한이 적용된다. → ❓확인 필요: 최대 글자 수(제안: 500자).

### FR-3. AI 감정 분석 + 공감 메시지 · **P0**
- 서버(API 라우트)에서 OpenRouter `google/gemma-4-31b-it:free` 호출.
- 모델에 JSON 응답 요청: `{ "emotion": "...", "message": "..." }`.
- 결과의 `emotion`·`empathy_message`를 `diary_entries`에 함께 저장.
- API 키는 **서버에서만** 사용(클라이언트 미노출).
- **수용 기준(AC)**:
  - [ ] 일기 저장 요청에 대해 감정 라벨과 공감 메시지가 응답에 포함된다.
  - [ ] 응답은 `{ emotion, message }` JSON으로 파싱된다.
  - [ ] 모델이 형식에 어긋난 응답을 줘도(파싱 실패) 앱이 크래시하지 않고 graceful하게 처리한다(재시도 또는 기본 메시지).
  - [ ] OpenRouter 실패·레이트리밋·타임아웃 시 사용자에게 이해 가능한 에러 메시지를 보여준다.
- **결정 필요(정책)**: AI 호출 실패 시 (a) 일기 자체는 저장하고 공감 메시지만 비운 채 보여줄지, (b) 저장 자체를 롤백할지. → ❓확인 필요 (제안: (a) — 사용자 글은 절대 잃지 않음).

### FR-4. 작성 결과 표시 · **P0**
- 작성 직후 같은 화면(또는 결과 영역)에 감정 라벨 + 공감 메시지를 카드 형태로 표시.
- **수용 기준(AC)**:
  - [ ] 저장 성공 시 방금 쓴 일기 내용, 감정, 공감 메시지가 함께 보인다.
  - [ ] 처리 중에는 로딩 인디케이터가, 실패 시에는 에러 상태와 재시도 수단이 보인다.

### FR-5. 히스토리(과거 일기 조회) · **P0**
- `GET /api/diary`로 현재 사용자의 일기만 최신순 조회.
- 각 항목: 날짜, 일기 내용, 감정, 공감 메시지.
- **수용 기준(AC)**:
  - [ ] 로그인 사용자 본인의 일기만 조회된다(타인 데이터 미노출).
  - [ ] 목록은 최신순(`created_at` DESC)으로 정렬된다.
  - [ ] 일기가 하나도 없으면 빈 상태(empty state) 안내가 보인다.

### FR-6. 로딩·에러·빈 상태 UI · **P0**
- 모든 비동기 흐름(로그인, 작성, 조회)에 로딩/에러/빈 상태 표현.
- **수용 기준(AC)**:
  - [ ] 각 화면이 로딩·에러·정상·빈 상태를 시각적으로 구분해 표시한다.

### FR-7. 일기 삭제 · **P1**
- 본인 일기 항목 삭제(하드 삭제).
- **수용 기준(AC)**:
  - [ ] 사용자는 자신의 일기를 삭제할 수 있고, 삭제 전 확인을 받는다.
  - [ ] 타인의 일기는 삭제할 수 없다(서버에서 소유권 검증).
- → ❓확인 필요: MVP(P0)에 포함할지, P1로 둘지. (현재 P1로 제안 — `PLAN.md` API 계약에 DELETE 미정의.)

### FR-8. 감정 흐름 시각화 / 통계 · **P2** (향후)
- 기간별 감정 분포·추세 차트. 이번 범위 밖(11장).

### FR-9. 일기 수정(편집) · **P2** (향후)
- 작성 후 내용 편집 및 재분석. 이번 범위 밖.

## 7. 비기능 요구사항 (Non-functional)

### 7.1 성능
- 무료 모델 지연을 고려해 서버 함수 타임아웃 대응: `maxDuration` 상향 또는 스트리밍(`PLAN.md`).
- 사용자에게는 작성 즉시 로딩 상태를 노출해 체감 지연을 완화한다.
- → ❓확인 필요: 목표 응답 시간 상한(제안: p95 15초 이내, 그 이상은 타임아웃 처리).

### 7.2 보안 / 프라이버시
- OpenRouter API 키·DB 자격증명은 서버 환경변수로만 관리(클라이언트 미노출, 저장소 커밋 금지, `.gitignore`).
- 모든 일기 API는 인증 필수, 서버에서 `user_id` 기준 소유권 검증(타 사용자 데이터 접근 차단).
- 구글 OAuth 자격증명, `AUTH_SECRET`은 배포 환경 변수로 관리.
- **저장소가 공개**이므로 비밀정보·개인정보가 코드/커밋에 포함되지 않도록 한다.
- → ❓확인 필요: 개인정보 처리방침/이용약관 필요 여부, 데이터 보관·삭제(계정 삭제 시 일기 파기) 정책.

### 7.3 접근성 (Accessibility)
- 합의된 톤: **따뜻하고 편안한 일기장** — 부드러운 색, 충분한 여백, 반응형, 접근성 준수.
- 명도 대비(WCAG AA 수준 지향), 키보드 내비게이션, 폼 요소 레이블/aria, 포커스 표시.
- 로딩/에러 상태를 스크린리더가 인지할 수 있게 표현(`aria-live` 등).

### 7.4 반응형 / 호환성
- 모바일·데스크톱 브라우저 대응(반응형 레이아웃).
- → ❓확인 필요: 지원 브라우저 하한(제안: 최신 크롬/사파리/엣지/파이어폭스).

### 7.5 확장성 / 안정성
- OpenRouter 실패·레이트리밋·JSON 파싱 실패에 대한 graceful degradation(FR-3).
- 데이터 모델·API 계약은 `PLAN.md` 확정본을 따른다(변경 금지 사항).

## 8. 데이터 모델 & API 계약 (확정 — 변경 금지)

> `PLAN.md`에서 확정된 사항. PRD 정합성을 위해 재기재한다.

### 8.1 데이터 모델 (PostgreSQL)
- **`users`**: `id`, `google_sub`(고유), `email`, `name`, `image`, `created_at`
- **`diary_entries`**: `id`, `user_id`(→ `users.id` FK), `content`, `emotion`, `empathy_message`, `created_at`

### 8.2 API 계약 (초안 — 1단계에서 확정)
- `POST /api/diary` — 요청 `{ content }` → 응답 `{ id, emotion, empathy_message, created_at }` (로그인 필요)
- `GET /api/diary` — 응답 `{ entries: [...] }` (로그인 사용자 것만)
- `/api/auth/*` — Auth.js 구글 로그인/콜백

### 8.3 AI 응답 형식 (확정)
- gemma 응답: `{ "emotion": "불안", "message": "오늘 많이 힘드셨겠어요…" }`
- 서버는 `emotion` → `diary_entries.emotion`, `message` → `diary_entries.empathy_message`로 매핑.

## 9. 화면 명세 (Screen Specification)

> 목적: 프런트엔드가 **별도 화면 설계 없이 병렬로** UI를 구현할 수 있도록 화면·요소·상태·톤을 구체적으로 정의한다. 픽셀 목업은 불필요.

### 9.0 공통 디자인 원칙 (전 화면 공통)
- **톤 & 무드**: 따뜻하고 편안한 일기장. 부드러운 파스텔/뉴트럴 색조, 넉넉한 여백, 라운드 처리된 카드, 과하지 않은 그림자. 자극적이지 않고 차분한 분위기.
- **타이포**: 가독성 높은 본문, 일기 내용은 살짝 큰 본문 크기로 편안하게.
- **반응형**: 모바일 우선. 데스크톱에서는 가운데 정렬된 최대 폭(제안: 640~720px) 컬럼.
- **접근성**: WCAG AA 대비, 키보드 포커스 가시화, 폼 레이블/aria, 로딩·에러 `aria-live`.
- **공통 상태**: 모든 데이터 화면은 로딩 / 정상 / 에러 / 빈 상태를 갖는다.
- **네비게이션**: 로그인 후 상단 또는 하단에 "작성 ↔ 히스토리" 이동 수단, 사용자 프로필(이미지/이름)과 로그아웃.
- → ❓확인 필요: 브랜드 컬러 팔레트/로고 확정값(현재는 위 톤 가이드만).

### 9.1 화면 ① — 로그인 (`/` 또는 `/login`)
- **목적**: 서비스 소개 + 구글 로그인 진입.
- **핵심 UI 요소**:
  - 서비스 이름/로고 + 한 줄 소개("한 줄 일기에 AI가 공감해 주는 다이어리").
  - **[구글로 계속하기]** 버튼(구글 브랜드 가이드 준수 아이콘 포함).
  - 간단한 가치 제안(감정 분석·공감 메시지·나만의 기록) 1~3줄.
- **상태/동작**: 로그인 진행 중 로딩; 로그인 성공 → 작성 화면 리디렉션; 이미 로그인된 사용자가 접근 시 작성 화면으로 자동 이동.
- **톤**: 첫인상에서 "따뜻하고 안전한 공간"이 느껴지도록 부드러운 배경.

### 9.2 화면 ② — 일기 작성 + 결과 (`/write`)
- **목적**: 한 줄 일기 작성 → AI 감정·공감 즉시 확인.
- **핵심 UI 요소**:
  - 인사/날짜 헤더(예: "오늘 하루는 어땠나요?", 오늘 날짜).
  - **일기 입력 영역**: 멀티라인 텍스트박스(placeholder 예: "오늘의 마음을 한 줄로 적어보세요"), 글자 수 표시(최대치 대비).
  - **[기록하기] 버튼**: 빈 입력 시 비활성.
  - **결과 카드**(작성 후 노출): 방금 쓴 일기 내용 + **감정 라벨**(뱃지/칩) + **공감 메시지**(부드러운 카드). 따뜻한 마무리 느낌.
  - 상단/하단: 히스토리로 이동 링크, 프로필·로그아웃.
- **상태**:
  - 로딩: 전송~AI 응답 대기 시 인디케이터("마음을 읽는 중…" 등 부드러운 문구).
  - 성공: 결과 카드 노출.
  - 에러: AI/네트워크 실패 시 에러 메시지 + 재시도. (일기 저장 정책은 FR-3 결정에 따름.)
- **인증**: 미로그인 접근 시 로그인 화면 리디렉션.

### 9.3 화면 ③ — 히스토리 (`/history`)
- **목적**: 과거 일기와 감정을 되돌아보기.
- **핵심 UI 요소**:
  - 화면 제목(예: "지난 기록").
  - **일기 목록**(최신순): 각 항목 카드 = 날짜 + 일기 내용 + 감정 라벨(칩) + 공감 메시지(요약 또는 전체).
  - (P1) 각 항목 삭제 버튼(확인 다이얼로그 동반).
  - 상단/하단: 작성 화면으로 이동, 프로필·로그아웃.
- **상태**:
  - 로딩: 목록 스켈레톤/스피너.
  - 빈 상태: "아직 기록이 없어요. 첫 한 줄을 남겨보세요" + 작성 화면 CTA.
  - 에러: 조회 실패 메시지 + 재시도.
- **인증**: 본인 데이터만 표시(서버 검증), 미로그인 접근 시 리디렉션.

> **화면 흐름**: 로그인(①) → 작성+결과(②) ⇄ 히스토리(③). 로그아웃 시 ①로 복귀.

## 10. 성공 지표 (Success Metrics)

> MVP 검증 관점의 KPI. 정량 목표값은 초기 가설이며 배포 후 보정한다.

- **활성화(Activation)**: 로그인한 사용자 중 **첫 일기 작성 완료율 ≥ 60%**.
- **핵심 상호작용 성공률**: 일기 작성 요청 대비 **AI 공감 메시지 정상 응답률 ≥ 95%**(파싱·타임아웃 실패 < 5%).
- **응답 성능**: 작성→결과 표시 **p95 ≤ 15초**(무료 모델 기준, 7.1 참조).
- **리텐션(재방문)**: 최초 작성 사용자의 **7일 내 재작성률 ≥ 30%**.
- **안정성**: 인증·소유권 위반으로 인한 **타 사용자 데이터 노출 건수 = 0**.
- → ❓확인 필요: 측정 도구(예: Vercel Analytics/자체 로깅) 및 목표값 확정, 초기 목표 사용자 규모.

## 12. 가정·제약·리스크 (Assumptions & Risks)

### 12.1 가정 (Assumptions)
- 사용자는 구글 계정을 보유하고 있으며, 구글 로그인만으로 충분하다.
- 무료 모델(`google/gemma-4-31b-it:free`)이 한국어 감정 분석·공감 메시지 품질을 실용 수준으로 제공한다.
- 3장 페르소나·문제 정의는 콘셉트 기반 가정(리서치 미검증).

### 12.2 제약 (Constraints)
- 스택 고정: Next.js(App Router)+Vercel / PostgreSQL(AWS) / OpenRouter gemma:free / Auth.js 구글.
- 데이터 모델·AI 응답 형식은 **변경 금지**(8장).
- 저장소 공개 → 비밀정보 커밋 금지.
- Vercel 서버리스 함수 실행 시간 제한.

### 12.3 리스크 (Risks) & 완화
| 리스크 | 영향 | 완화 |
|---|---|---|
| 무료 모델 응답 지연/타임아웃 | 작성 실패·이탈 | `maxDuration` 상향·스트리밍, 로딩 UX, p95 목표(7.1) |
| 모델의 비정형(JSON 깨짐) 응답 | 파싱 실패 | 견고한 파싱·재시도·기본 메시지(FR-3 AC) |
| OpenRouter 레이트리밋/장애 | 기능 중단 | graceful 에러 처리, 사용자 재시도 안내 |
| 무료 모델의 한국어 공감 품질 미흡 | 핵심 가치 저하 | 프롬프트 튜닝, 필요 시 모델 교체 검토(범위 밖) → ❓확인 필요 |
| 공개 저장소 비밀정보 노출 | 보안 사고 | `.gitignore`·환경변수·리뷰 |
| 정서적 위기 발화(자해 등) 대응 부재 | 안전 이슈 | ❓확인 필요: 위기 문구 감지 시 안전 안내(핫라인) 노출 정책 |
| 남용/스팸(무제한 호출) | 비용·성능 | ❓확인 필요: 사용자당 요청 레이트리밋 정책 |
